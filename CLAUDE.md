# ableton-scaffold

Song-agnostic tooling for Ableton Live music production with Claude Code: a bridge to the
running session, a set of specialist agents, slash commands, and the conventions that keep
their output trustworthy.

**No song content lives here, ever.** Songs live in their own private repos, one per track.
This one holds method.

---

## Read this first: critical conventions

**Pitch: C3 = MIDI 60.** Ableton's own convention, and the one every file here uses. Other
tools and older documents use C4 = 60, and note names from those read one octave high.
When in doubt, trust the MIDI number, never the note name.

**Arrangement view, not Session view.** Songs are composed in the Arrangement. AbletonMCP
writes to Session clips only, so use it for MIDI drafting and drag the clip to the
Arrangement afterwards. The bridge scripts talk to AbletonOSC, which is arrangement-aware.

**No em-dashes. No AI-speak. No therapy-speak.**

**Plugin parameters always in real UI units**, with meter mode and resting-vs-swing
specified. "Decay Rate: 2.4 s" is a usable instruction. "Increase the decay" is not.

## Where songs live

Song folders are outside this repo. Every bridge script resolves the songs directory the
same way, first hit wins:

1. `--songs-dir` on the command line
2. `$ABLETON_SONGS_DIR`
3. `./songs` under the working directory
4. `<this repo>/songs`

The usual setup is `export ABLETON_SONGS_DIR=~/music-studio` with each track repo checked
out underneath it. See `bridge/README.md`.

A track repo looks like this. Only the hand-written files are worth versioning; `parts/`
and `chain/` are regenerated by `/pull`.

```
<song-name>/
  brief.md          backstory, artistic principles, influences, production rules
  structure.md      section map with bar ranges, tempo, key, time signature
  harmony.md        chord map per section, voice-leading notes
  lyrics.md         lyrics tagged by section, canonical text
  log.md            decisions and reasoning, append-only, newest last
  conflicts.md      known discrepancies needing the session to resolve
  midi-patterns.md  note-level part documentation
  returns.md        return track inventory
  files.md          project file inventory
  parts/            drums/ bass/ guitars/ keys/ vocals/ fx/   (generated)
  chain/            one .md per track, device list and parameters (generated)
  mix/              spectrograph captures plus readings.md
```

Create one with `bin/new-song <name>`. It writes the track repo's own `CLAUDE.md` and
symlinks these agents and commands into its `.claude/`, without which a session started
there sees none of them. Never create a track repo inside this one.

## Starting a session

1. Ask which song, or read it from context.
2. Read that song's `brief.md`, `structure.md` and `log.md` before anything else.
3. Read `harmony.md` and `lyrics.md` when the session touches those areas.
4. Run `/pull` to sync the session state into `parts/` and `chain/`.
5. Append decisions to `log.md` before the session ends.

## Ending a session

1. Append the `/log` entry: what changed, what was decided, what is still open.
2. Flag anything newly contradictory into the song's `conflicts.md`.
3. Ask what was learned that is not about this song: a tool limit, a plugin's behaviour, a
   way of working that failed or held. Write it here, in the scaffold, where the next song
   will read it. Method rules go in this file, bridge and OSC behaviour in
   `bridge/README.md`, install and rig facts in `SETUP.md`, handler notes in
   `abletonosc-ext/README.md`. Strip the song out of it first: no track names, no lyrics,
   no clip or file names. This repo is public and the song is not.
4. Commit and push the track repo. If the scaffold changed, commit and push it too. Check
   that local and remote match before calling the session closed.

A commit that is never pushed is not a backup, and a lesson left in one song's log is not
method. On one project, a month of sessions closed on local commits only, and everything
learned about the bridge in that time sat in that song's log where no other song would
find it.

## Method, and why each rule is here

These cost real time to learn. They are the reason this repo exists separately from any
one song.

**Vendor documentation beats any secondary table.** Manuals, keymaps and official PDFs
win over a screenshot, a spreadsheet, a wiki page or training data. On one machine, three
loose drum-map files all disagreed with the vendor keymap and with each other, while the
real keymap sat unused in the manuals folder the whole time. Programming from any of them
would have written onto the wrong articulations throughout.

**Verify documentation against the session before trusting it.** Documentation drifts and
nothing contradicts it until someone checks. One day of checking against a real session
turned up a wrong intro length, three wrong section lengths, a mislabelled chord, a
superseded bridge arrangement, a wrong drum-map note, three wrong return tracks and a
silent velocity bug. Assume the same rate.

**The session is source of truth; pull output is a cache.** Gitignore `parts/` and
`chain/` in the track repo. They can always be rebuilt.

**Raw parameter values are per-parameter scales, not normalized.** On one Gate, Threshold
reads 0.1825 for "-36.6 dB" while Floor reads -40.0 for "-40.0 dB". Never infer units from
a raw value, and never hand-write a conversion table. `str_for_value`, exposed as
`/live/device/get/parameter/value_string`, is the only trustworthy source of UI units. It
costs one round trip per parameter, so use it per device on demand, never across a whole
session.

**Some plugins expose almost nothing.** FabFilter Pro-R publishes a single parameter
(`Device On`) unless mapped in Live's Configure mode. VST3s such as AmpliTube show generic
`Param 1..N`. Check what a device actually publishes before promising to read its chain.

**Distinguish audio-to-MIDI conversion tracks from programmed MIDI.** Irregular starts
like `11.4986` with fractional durations are pitch detection output, not performance.
Mixing them into analysis produces confident wrong answers about a part.

**When a document and the session disagree, record it rather than silently picking one.**
That is what `conflicts.md` is for, and closing an entry there is worth a `/log` line.

**A read-back is not proof the change is audible, or that it is where the user thinks it
is.** When someone at the desk doubts a write landed, give a test with a binary result
they can see on the panel in front of them: a button that lights, a knob that moves. Say
which panel. A meter delta that another cause could explain (the patch's own LFO, for one)
is not evidence. Label estimates as estimates, and name the manual a number came from,
after checking it is the manual for the device in the room and not its sibling.

**Timbre is an ear call; measurement is for placement and level afterwards.** On a sound
design pass, make or propose one change, say what changed and why, and wait for the
listen. Capture only when asked to. One pass ran twelve captures on a voice that was then
rejected by ear in a sentence: measurement had been choosing the sound. Keep the previous
state recoverable.

**Check the octave of a converted vocal against its source audio.** Live's Convert Melody
has written a sung line twelve semitones high. Read at face value, that puts the whole
voice in the wrong register against the bass and every unison or register call after it is
wrong. Check the spectrum of a long note in the source audio first and state the
correction. Conversion also turns creaky onsets into short quiet notes, drops quiet
phrases, and merges syllables, so count notes against syllables before trusting it.

**A clip's time 0 is its marker 0, not its left edge.** Live counts clip time from the
start marker, and a clip that was trimmed, split or had its contents dragged has a marker
that is not 0. A note read that assumes clip time 0 sits at the clip's start on the timeline
reports every position off by the marker, and the error is silent: the numbers look right
and the user, who hears the clip, is the one who catches it. That happened on 2026-11-08
with a vocal guide whose marker sat eight beats in: a day of positions two bars late, an
overlap that did not exist, and a comp called misaligned when it was not. The bridge's note
handlers now convert, so song beat = clip start plus reported time for every clip. The
general rule stands for any other read: before quoting a timeline position from inside a
clip, read its markers.

**A vocal guide follows the singer's rhythm and changes pitch only.** A guide composed to
the grid was rejected as unsingable even though its syllable counts were right. Build the
guide from a syllable map of the singer's own take (forced alignment of the known lyric
works), keep their onsets and lengths, put each note on the syllable's vowel and not on
its opening consonant, run notes into each other inside a line, and audition it on a
sustained sound, not a plucked one. Show the syllable map before writing a clip.

**Adding or removing bars: the parts' cycles set the length and the fill.** When parts
loop at different lengths (a 2-bar drum pattern against a 3-bar bass cell, say), an insert
that keeps both in step is a multiple of each, and each part needs its own fill. "Repeat
the N bars before the seam" suits one cycle and breaks another: on one song the drums were
right and the bass jumped from the end of its lap back into the middle of it, which the
user heard at once. For each part, check that every join the edit creates is one the song
already makes somewhere (a cell repeating, the lap turning round). Copies of MIDI parts
can start or stop mid-phrase at the clip edge; capture across each join before calling it
done. Inserted and deleted time moves every later bar number, so rewrite the section map
at once and note the offset for older documents.

**Start with the smallest change that answers the note.** Asked for a breath between two
sung sections, a 6-bar insert was advised because it kept every cycle whole; the user
heard a new section and wanted a 2-bar tag. Offer the shortest length the cycles allow
first. And do not cut time elsewhere only to restore the old length or bar numbers: on the
same song a 2-bar cut was offered to win back the seconds, and on review it fixed nothing
the listener would hear.

**Record what a print sounds, measured, not the edit someone described.** A log entry
recorded a +12 transposition from a reading of the conversation; the print measured +7 from
a different harmonic than assumed. Pitch-track a print before writing its note into the
docs.

**A clip gain on a consolidated clip is bookkeeping, not a level decision.** Consolidate
normalises the new file and puts the difference in clip gain, so the dB on the clip says
nothing about what anyone chose. A session close once logged such a figure as the singer's
level call for a layer; the layer played about 8 dB above what the log implied, and the
person did not recognise the decision when it was read back. Before quoting a clip gain,
read the clip's file path: a consolidated file or a file peak at 0 dBFS means report what
plays (file level plus gain), phrase by phrase, and say whose move it was only if they
said so.

**Check a throw against the word's sounds, not the word.** A send ride drawn by eye over a
waveform was meant for one word and covered three; another peaked on a word's vowel and
had fallen away by its consonant, which was the sound the throw was for. Read the lane
back, take syllable onsets from the vocal guide clip, and find the consonants with a
high-passed envelope of the print (sibilants show above 5 kHz where the body band goes
quiet). Report both in the ruler's own positions. A throw cannot bring out a sound the
take does not have: measure the consonant against a neighbouring one before shaping the
lane around it.

**When a layer feels weaker in one section, compare what reaches the fader.** Read the
fader, pan and sends at a few points in every section first; if they match, the setting is
not the cause. Then measure the layer against its lead per phrase in each section: the
sustained level (gated RMS), not only the loudest window, and the share of energy in 2.5
to 5 kHz. On one song the loudest windows matched in all four sections while the body sat
2 dB lower and darker in the one that lacked punch, which pointed at the delivery and
away from the mixer.

**Live's Save As moves the open set onto the new file.** A copy saved "as a backup" before
an edit becomes the file being edited, and the old name keeps the old state. Read the
locators out of each `.als` on disk (gzip XML, `Locator` elements) to say which file holds
which version before recording it.

**Review a part against its plan before proposing changes to it.** Lay what the documents
planned for the part beside what the set holds, section by section, and line it up with
the parts around it (bass cycle, sung syllables, other layers) from one read of the set.
On one song a drum lane judged for "variety" turned out to have a sound two-bar cell and
three unbuilt steps of its own planned orchestration, plus its named effect sitting at a
send level too low to hear. The opportunities were the unbuilt plan, not edits to the cell.

**Do not "fix" what was chosen deliberately.** Out-of-key notes, an unresolved ending, a
drumless outro and an empty track are as likely to be intentional as they are to be
mistakes. Ask before correcting anything that reads as a deviation.

## Slash commands

| Command | What it does |
|---|---|
| `/pull` | Sync Ableton arrangement into the song folder (tracks, clips, devices, tempo) |
| `/push <part-file>` | Write notes from a part file into an Ableton Session clip |
| `/device <track> <device> <param> [value]` | Read or set a device parameter by name |
| `/log <message>` | Append a dated decision entry to the active song's log.md |
| `/song <name>` | Switch active song context, or scaffold a new track repo |

## Agents

| Agent | File scope | When to use |
|---|---|---|
| `orchestrator` | structure.md, log.md | Full arrangement passes; routing work |
| `structure` | structure.md, sections | Section editing, bar map, cue points |
| `harmony` | harmony.md, melodic and vocal parts | Chord map, voice-leading, melodic parts |
| `rhythm` | parts/drums, parts/percussion | Groove, drum programming |
| `mix-chain` | chain/, mix/, reference/manuals/ | Device config, mix decisions, spectrograph reads |

## Tools

**AbletonMCP**, TCP 9877, Session clips only.

- Reliable sequence: `create_clip`, then `add_notes_to_clip`, then `set_clip_name`
- Frozen tracks fail silently. Unfreeze first.
- `get_session_info` time signature values are not reliable. Cross-check against the
  transport bar.

**AbletonOSC**, UDP 11000 listen and 11001 reply. Arrangement clips, device parameters,
track meters, return tracks. Install per SETUP.md; the bridge scripts live in `bridge/`
and the extra handlers they need are in `abletonosc-ext/`.

- Live 11 embeds CPython 3.7. Run `bridge/check_py37.py` before copying anything into
  Remote Scripts.
- Adding a new handler class needs a full Ableton restart, not a reload and not a control
  surface toggle.
